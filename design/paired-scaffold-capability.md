# Paired-Scaffold Capability — Design

**Owner:** architect
**Workflow:** `/studio:design` — PM ✓ Marketer ✓ CD ✓ DE (Plan Review → REVISE) → revised → DE (re-review → PROCEED) ✓
**Status:** Design locked, gate-cleared. Engineering spec at [`../specs/paired-scaffold-capability.md`](../specs/paired-scaffold-capability.md).
**Date:** 2026-05-26

---

## Decision

`init` scaffolds a paired **PRODUCTION + CANVAS + SHARED** workspace where SHARED is *included by reference, never copied or published* — so prototypes are built from real components and graduate to production instead of being throwaway. Per-stack scaffold blueprints live in engineer specialists; `init` records a minimal manifest in `project-context.md`; skills consume that manifest as a thin pointer.

---

## 1 · Contract (stack-neutral)

**Roles** under one declared `code_root` (canonical names: `code/app`, `code/canvas`, `code/shared`):

- **PRODUCTION** includes SHARED by reference; never includes CANVAS.
- **CANVAS** includes the *same* SHARED by the *same* reference; no app services (no db / auth / sync).
- **SHARED** = tokens, type, color, spacing, motion, components, assets; depends on neither.

**Invariants:**

- **INCLUDED-BY-REFERENCE.** SHARED is included by reference, never copied or published. `local-path` (SPM / pnpm workspace) and `project-inclusion` (Gradle `include(":shared")` + `implementation(project(":shared"))`) are two *instances* of one invariant.
- **NO-FORK.** A component lives once (in SHARED); both targets link it; editing in canvas edits production with zero sync step. A `// Synced from…` comment or a duplicated component file is a violation.

**Scope boundary** (structural, not categorical): the scaffold applies *where a shared front-end module exists*. A different shared primitive (schema, API contract, model artifact) is a different scaffold shape and a separate brief.

**Shape rule:**

- **Triple** — shared front-end module spans ≥2 surfaces AND prototyping is in the workflow.
- **Collapse** — app + canvas, no SHARED (no design system, or it's external).
- **App-only** — no prototyping.

Each shape has its own manifest shape and lint expectation, so the no-fork check does not false-positive on a project that legitimately has no SHARED module.

## 2 · Swift (Apple) instance

One scaffold serves all Apple platforms; `platform` is a manifest key (`ios` | `macos` | `multiplatform`). Specialist = `swift-engineer`.

- `code/shared` = local Swift Package — library target; resources via `.process`; `platforms:` from `platform`.
- **Project generation (default).** `app` + `canvas` `.xcodeproj` are generated by **XcodeGen** from `project.yml`, which *declares* the `../shared` package dependency. `xcodegen generate` ≈ `pnpm install` — wiring regenerated from one declared source; the dependency edge is a lintable file, not an Xcode UI action.
- **Escape hatch.** Teams declining XcodeGen use the manual path → `scaffold_state: manual`. The manual path forgoes *generation*; invariant enforcement (R3 no-fork, included-by-reference) still applies.
- `.gitignore`: commit `project.yml` + `Package.swift`; `.xcodeproj` is a generated artifact, gitignored as default.
- Fonts / resources via `Bundle.module`, one shared `register()` call site for both targets.

---

## 3 · Web instance

`code/shared` = workspace package. Root `code/package.json` declares the workspace; `app` + `canvas` depend on it; `pnpm install` symlinks, no publish. Reference by package name, not by tsconfig path-alias (avoids resolution drift). Canvas = Storybook (default) or Ladle (`canvas_framework`).

---

## 4 · Specialist blueprint contract

Each engineer specialist carries four scaffold sections — **Layout · Sharing Mechanism · Resource Handling · Scaffold Commands** (the *single home* for commands, parameterized by derived paths; commands do not live in the manifest). The template gains a mandatory `Scaffold Blueprint (<stack>)` section. Specialists declare `stack:` in YAML frontmatter (drives R2 of the lint; see §8).

**Android** is the template's third-mechanism validation example — Gradle project-inclusion as a third instance of INCLUDED-BY-REFERENCE — paper proof the contract holds unchanged across a mechanically-different stack. Not a shipped specialist; the worked example proves the abstraction is honest.

## 5 · init execution (six steps)

| Step | Action |
|---|---|
| 0 | Pre-flight — if `scaffold_state` already present, surface rather than re-run |
| 1 | Ask stack → match specialist; if none matches, offer to generate one from the template |
| 2 | Ask "shared front-end module? + prototyping?" → triple \| collapse \| app-only; if triple, ask the shared module *import* name in the same exchange |
| 3 | Create role dirs from the blueprint; initialize the shared module (`Package.swift` / `package.json` + root workspace) |
| 4 | Wire the by-reference dep — web: root `package.json` + `pnpm install` (auto-completes); Swift: write `project.yml` + `xcodegen generate` (default) or record `scaffold_state: manual` (escape hatch) |
| 5 | Write the manifest (contract block + scaffold block) to `project-context.md` |
| 6 | Verify build; on success flip `scaffold_state → complete` |

`/studio:init --update` handles shape promotions (`app-only → collapse`, `collapse → triple`, etc.) and the `manual → complete` conversion (write `project.yml`, regenerate, verify). Shape demotion is not supported.

## 6 · Manifest (reduced + grouped)

*Derivability test: if two correct runs on the same answers can't differ, don't store it.*

**Contract block** — every skill reads:
`stack`, `code_root`, `shared_module_name` (import name; package name derived by convention), `sharing_mechanism`, `platform` (Apple), `package_manager` + `canvas_framework` (web), `spec_path`, `decisions_path`.

**Scaffold block** — one-time state:
`scaffold_state` (`none` | `manual` | `complete`), `generation_tool` (`xcodegen` | `none`).

**Dropped (derivable, never stored):**

- `*_path` keys — derive from `code_root` + canonical names.
- `*_cmd` keys — stack constants; moved into the specialist blueprint so a blueprint fix reaches all projects (storing resolved strings was a single-source leak).
- Scheme keys — derive by convention; record only if the convention is broken.

Full schema in spec §A.

## 7 · Thin-pointer contract

Read `project-context.md` → take the contract keys → derive paths from `code_root` → read commands from the specialist selected by `stack` (parse its `Scaffold Commands` anchor — see spec §B). Never hardcode a path; never restate a command. Missing key → "run `/studio:init --update`".

---

## 8 · Lint (structural)

`evals/lint-agnostic.sh`, called by the suite runner. Five rules — full spec in §C.

- **R1** Narrow product-name grep — product names + hardcoded `studio_os/` banned in `agents/**` + `skills/**`.
- **R2** Stack-token placement by `stack:` frontmatter, **bidirectional** — stack tokens permitted ONLY in files declaring `stack:`; FAIL if a stack token appears in a file without `stack:` (incl. a stack token leaking into a skill or Core agent — the seam breach).
- **R3** No-fork / drift check — FAIL on canvas↔shared content duplication, OR on `#filePath` resource loading when `sharing_mechanism: spm-local`. (The check that would have caught Log.)
- **R4** Skills don't hardcode paths — literal paths not formatted as `{key}` references in `skills/**` → WARN; product-token paths → FAIL per R1.
- **R5** Specialist `Scaffold Commands` anchor block presence — exactly one ` ```scaffold-commands ` block per specialist; FAIL on absent / duplicate / malformed.

R1 + R3 + an **included-by-reference check** wire into the eval suite — invariants enforced, not asserted. The manual path (`scaffold_state: manual`) does *not* disable enforcement; it forgoes generation only.

## 9 · Log reconciliation = first proof obligation

The capability is **not validated** until run back on Log to close the fork it diagnosed. Log currently violates the core invariant — its canvas `DesignTokens.swift` is a manual copy (`// Synced from Log/…`), fonts use a `#filePath` hack instead of `Bundle.module`, and `design-system/` is HTML documentation, not a Swift module. The reconciliation:

- `design-system/` → real Swift Package root (HTML docs → `design/`).
- Canvas `DesignTokens.swift` fork → `import AppDesignSystem`.
- `#filePath` font loader → `Bundle.module`.
- Adopt XcodeGen for Log's `app` + `canvas` (one-time `.pbxproj` → generated migration cost; bounded and one-time).

This reconciliation **is** the Swift validation run that graduates `swift-engineer` to a validated default. Full sequence in spec §H.

## 10 · Default bundle (validation-gated)

Ship a specialist as default only when its blueprint runs end-to-end and builds.

| Stack | Disposition | Why |
|---|---|---|
| `swift-engineer` | Default, validated via §9 | Log is the witness, post-reconciliation |
| `web-engineer` | Default — validation launch-blocking | Largest UI constituency; must not ship as a stub |
| Android / React Native / Flutter | Visible on-demand generation + public roadmap | Graduate as runs validate them |
| Backend / data / ML | Out of scope — separate scaffold-shape brief | The triple is a front-end pattern |

**On-demand specialist generation is a first-class, visible feature** ("I'll generate a specialist for your stack now") — not a silent fallback. It is the engine of bundle growth: demand surfaces a stack → on-demand generation serves it → real runs validate it → validated ones graduate to default. The marketplace itself becomes the validation pipeline.

## Open questions (resolved)

- **Tuist as a Swift generator alternative** — *deferred.* XcodeGen's `project.yml` satisfies the invariant; Tuist's Swift DSL adds inversion (Swift describing Swift) without a corresponding win. Ship one generator. Revisit only if a specific install requires it.
- **Generated `.xcodeproj` gitignored vs committed** — *gitignored, as default not suggestion.* The whole point of declarative generation is that `project.yml` is the source of truth.
